# 포근 마을 (Cozy Village)

## 프로젝트 분석 및 고도화 핸드오프 문서

-   문서 버전: 2.0
-   목적: Claude Code 등 다른 AI 개발 에이전트에 프로젝트를 인계하고,
    기존 구현을 분석한 뒤 단계적으로 고도화하기 위한 통합 문서
-   기준 자료: 사용자가 제공한 `PROJECT_PROMPT.md` 및 대화에서 정리한
    개선 방향
-   중요 원칙: 이 문서는 프로젝트 설명과 개선 지침이다. 실제 소스 코드의
    구현 상태를 증명하지 않는다. 반드시 저장소를 직접 조사해 사실 여부를
    확인한다.

# 1. 핸드오프 요약

## 1.1 프로젝트 한 줄 소개

**포근 마을**은 동물의 숲식 마을 생활, 디아블로식 핵앤슬래시와 장비
파밍, 야생의 땅: 듀랑고식 오픈월드 생존·건설·공룡 길들이기, XP 히어로식
서바이벌 아레나를 결합한 브라우저 기반 3D 게임이다.

설치 없이 브라우저에서 실행하는 것을 목표로 하며, 싱글플레이를 기반으로
향후 소규모 멀티플레이까지 지원하는 방향이다.

## 1.2 개발 방향 요약

프로젝트의 다음 발전 방향은 단순히 기능을 추가하는 것이 아니다.

1.  기존 구현과 데이터의 안정성을 확보한다.
2.  캐릭터·주민·몬스터·배경의 그래픽 스타일을 통일한다.
3.  전투·파밍·생활·제작·건설·탐험이 서로 연결되는 게임 루프를 만든다.
4.  무한 월드를 단순한 지형 반복이 아닌, 탐험할 가치가 있는 세계로
    발전시킨다.
5.  PC와 모바일에서 실측 가능한 성능 목표를 세우고 최적화한다.
6.  저장·계정·멀티플레이는 기반 시스템을 안정화한 뒤 단계적으로
    도입한다.

## 1.3 현재 가장 중요한 판단

기존 기획에는 이미 많은 시스템이 포함되어 있다. 따라서 신규 콘텐츠를
무작정 늘리기보다, 먼저 실제 구현 상태를 확인하고 다음 순서로 접근한다.

-   P0: 기존 기능 보호, 치명적 오류, 저장 데이터, 실행 안정성
-   P1: 캐릭터·주민·몬스터·애니메이션의 시각적 일관성
-   P2: 전투·아이템·파밍·던전의 핵심 재미
-   P3: 마을 생활·거점·생태계·오픈월드 콘텐츠의 연결
-   P4: PC/모바일 성능 및 UX
-   P5: 계정·클라우드 저장·서버 권한 멀티플레이 및 장기 운영

이 순서는 실제 저장소 진단 결과에 따라 조정한다.

# 2. 기존 프로젝트 설명 (기준 자료)

아래 내용은 기존 `PROJECT_PROMPT.md`에 기재된 프로젝트 설명을 정리한
것이다. 실제 코드와 다를 수 있으므로 인계받은 개발 에이전트는 반드시
소스 코드와 대조해야 한다.

## 2.1 기술 구성

-   클라이언트: `index.html` 단일 파일 중심, 약 3,650줄 / 380KB로
    설명되어 있음
-   빌드 도구 없이 바닐라 JavaScript ES 모듈 사용
-   렌더링: Three.js r187, jsDelivr CDN, import map
-   후처리: EffectComposer, UnrealBloom, GTAO, 자체 색보정 셰이더
-   그래픽: MeshStandard 기반 PBR, sRGB 색 관리, ACES 톤매핑
-   환경: 물리 기반 하늘, 태양 궤적, 노을·밤하늘·별, 하늘 그라데이션
    환경광, 대기 안개
-   저사양 대응: 실사 셰이더가 기기에서 깨지면 툰 셰이딩으로 대체한다고
    설명되어 있음
-   사운드: 별도 오디오 파일 없이 WebAudio 합성. 효과음, 비, 천둥 포함
-   서버: `server/server.js`, Node.js + ws, 약 90줄로 설명되어 있음
-   테스트: Playwright 및 소프트웨어 WebGL(SwiftShader) 기반 시나리오
    테스트
-   배포: Claude 아티팩트 미리보기 및 GitHub 저장소를 사용한다고
    설명되어 있음

### 기존 에셋

기준 문서에는 다음 에셋이 약 13MB, CC0로 기재되어 있다. 실제 파일 및
개별 라이선스는 반드시 다시 확인한다.

-   KayKit 모험가: 무기·방패, 구버전 캐릭터
-   Quaternius Universal Animation Library: 정상 비율 마네킹 및 동작
    19종
-   Quaternius Ultimate Stylized Nature: 나무·덤불·바위·풀·꽃 27종
-   Quaternius 공룡 4종: 티라노, 랩터, 트리케라톱스, 파라사우롤로푸스
-   Poly Haven 텍스처 12종(색상+노멀): 지형 6종,
    기와·판자·돌벽·회벽·나무·천

## 2.2 월드 구조

-   사실상 무한 월드: 1,048,576 × 1,048,576칸으로 설명되어 있으며
    중앙에서 시작
-   64칸 구역 단위로 좌표 기반 생성, 값 노이즈 FBM 사용
-   동일 좌표는 재방문해도 같은 지형이 되도록 설계
-   바이옴: 바다, 해변, 초원, 숲, 사막, 설원, 늪, 고원(절벽), 마을, 길,
    마왕령
-   16칸 청크를 플레이어 주변에서 스트리밍
-   나무·풀은 인스턴싱하고 바람에 흔들리는 구조
-   장소는 구역별 해시로 결정

### 주요 장소

-   마을: 상점, 여관, 의뢰 게시판, 이동석
-   동굴: 입구형 던전
-   고대 미궁: 33 × 33 돌벽 미로, 보스와 보물
-   몬스터 야영지, 유적, 이동석, 용의 소굴
-   마을은 가까운 이웃과 길로 연결되고 바다는 둑길로 연결
-   시작점에서 멀수록 위험도 별 1\~5 증가

### 시작 지역

-   포근 왕국 왕도: 포근성, 국왕, 근위병
-   포근 마을: 왕도 남쪽, 30 × 20칸, 동물 주민 4명, 과일나무, 연못,
    상점, 아레나 건물, 지하 던전 입구
-   마을 서쪽: 내 집. 실내에 들어가면 지붕과 앞벽이 사라지는 꾸미기 공간
-   왕도 북쪽 약 180칸: 마왕성

### 별도 공간

-   마을 지하 던전: 층 구조
-   마왕성: 층 구조
-   아레나: 입구로 들어가는 별도 장면
-   기준 문서상 스토리와 연결되어 있음

## 2.5 기존 문서에 기재된 한계

다음은 기존 프로젝트 설명에서 명시한 한계다. 현재도 유효한지는 코드 및
실행 테스트로 확인한다.

-   실제 GPU 기기에서 FPS 측정이 이루어지지 않음
-   실사 렌더링과 넓은 시야로 저사양 모바일에서 무거울 수 있음
-   새 구역 생성 시 순간 끊김 가능성
-   플레이어가 색칠된 마네킹에 가까워 얼굴·의상 디테일 부족
-   마을 동물 주민, 대부분 몬스터, 왕·경비병이 단순 도형 모델
-   실사 배경과 단순 모델의 화풍 불일치
-   코트·로브 자락이 다리를 따라 움직이지 않음
-   서버 권한이 없어 몬스터와 전투가 클라이언트별로 따로 계산됨
-   치트 방지 미흡
-   마을·집 내부에서 다른 플레이어가 보이지 않음
-   코드가 단일 파일에 집중되어 유지보수 어려움
-   테스트가 일부 브라우저 시나리오 중심
-   저장이 localStorage 중심이며 계정·클라우드 저장 없음
-   무한 월드의 장소 종류가 반복적
-   던전·아레나·마왕성 층이 별도 장면
-   3인칭 카메라의 지형 충돌 처리 미흡

# 3. 핵심 진단 및 개선 방향

이 절은 기존 설명에서 확인되는 한계와 일반적인 게임 개발 관점의 개선
제안을 구분해 정리한다. 실제 우선순위는 저장소 진단 후 확정한다.

## 3.1 그래픽과 아트 디렉션

### 확인된 문제(기존 문서 기준)

-   플레이어 모델의 얼굴과 의상 디테일 부족
-   주민과 몬스터의 단순 도형 조합
-   배경과 캐릭터의 화풍 불일치
-   의상 자락 애니메이션의 부자연스러움

### 개선 제안

-   전체 게임의 아트 디렉션을 Stylized 3D 기준으로 정리한다.
-   플레이어, 주민, 몬스터, NPC, 장비, 건물의 재질·비율·색상·디테일
    수준을 통일한다.
-   기존 CC0 모델을 먼저 조사하고 재사용 가능성을 평가한다.
-   부족한 핵심 모델만 우선 교체한다.
-   캐릭터 외형과 장비 메시를 분리해 장비 변경이 실제 외형에 반영되도록
    한다.
-   리깅, 스킨 웨이트, 애니메이션 블렌딩을 검증한다.
-   AI 콘셉트 이미지와 실제 게임에서 쓸 수 있는 3D 모델을 구분한다.

### 캐릭터 애니메이션 후보

-   Idle
-   Walk
-   Run / Sprint
-   Jump
-   Attack
-   Skill
-   Dodge
-   Hit
-   Death
-   Gather
-   Fishing
-   Interaction

실제 필요한 동작을 우선순위로 나누고, 모든 캐릭터에 모든 동작을 무조건
적용하지 않는다.

## 3.2 살아 있는 마을

### 개선 제안

-   주민별 성격과 선호도
-   하루 생활 일정
-   시간대별 활동 장소
-   호감도 및 관계 단계
-   고유 대화와 의뢰
-   계절 및 날씨에 따른 반응
-   마을 발전에 따른 외형 변화
-   플레이어의 행동이 주민과 마을에 미치는 영향

주민 시스템은 대사량만 늘리는 방식이 아니라, 일정·상호작용·보상으로 실제
게임 플레이에 연결한다.

## 3.3 몬스터와 생태계

### 개선 제안

-   바이옴별 고유 몬스터
-   서식지와 활동 시간
-   먹이 및 포식 관계(필요한 범위부터)
-   경계·추적·후퇴·귀환 등 AI 상태
-   희귀 개체 및 변종
-   정예 몬스터와 지역 보스
-   생물별 전용 드롭 및 제작 재료
-   공룡 길들이기와 전투 동료 역할 구분

몬스터 수만 늘리기보다 각 종의 행동과 보상에 차이를 둔다.

## 3.4 오픈월드의 탐험 가치

무한 월드의 크기보다 콘텐츠 밀도와 지역 정체성을 우선한다.

바이옴별로 다음 요소를 설계한다.

-   고유 자원
-   고유 생물
-   고유 몬스터
-   지역 보스
-   전용 던전
-   숨겨진 장소
-   환경 이벤트
-   탐험 도감 및 발견 보상
-   위험도에 따른 보상과 준비 필요성

동일한 지형과 장소가 과도하게 반복되지 않도록 생성 규칙을 평가한다. 무한
월드 생성 자체를 복잡하게 만들기 전에, 대표 지역 몇 곳의 완성도를 높여
재미를 검증한다.

## 3.5 전투와 파밍

### 개선 제안

-   공격 판정과 애니메이션 타이밍 일치
-   피격 리액션 및 경직
-   스킬별 역할 구분
-   몬스터의 공격 예고
-   보스 페이즈별 패턴
-   드롭 연출과 희귀도 전달
-   장비 옵션 간 시너지
-   빌드 다양성
-   제작과 파밍의 상호 보완

아이템 희귀도만 높이는 것이 아니라, 획득한 장비가 플레이 방식에 의미
있는 변화를 주도록 한다.

## 3.6 생활·제작·건설의 통합

기존 채집·제작·건설이 전투와 분리된 별도 활동으로 남지 않도록 연결한다.

예시 루프:

탐험 → 자원 채집 → 위험 지역 전투 → 재료 획득 → 제작·장비 강화 → 거점
시설 확장 → 더 어려운 지역 탐험

-   농장: 식량 및 제작 재료 공급
-   작업장: 채집 재료 가공
-   대장간: 무기·방어구 제작 및 강화
-   창고: 자원 관리
-   사육장: 동물 및 공룡 관리
-   거점 방어: 특정 이벤트와 연계
-   주민 배치: 시설 생산 또는 편의 기능

이 기능들은 게임 밸런스와 구현 난이도를 검토한 후 단계적으로 도입한다.

## 3.7 기술 구조와 성능

### 개선 제안

-   단일 HTML을 한 번에 전면 재작성하지 않는다.
-   기능별 모듈 분리를 점진적으로 진행한다.
-   Three.js 렌더링 및 월드 생성 코드를 게임 로직과 분리한다.
-   게임 데이터와 UI 표시 로직을 분리한다.
-   청크 로딩·언로딩, 메모리 해제, 에셋 캐시를 점검한다.
-   InstancedMesh, LOD, Frustum Culling, Object Pooling 적용 여부를
    검토한다.
-   후처리 효과를 기기 성능별로 조절한다.
-   실제 GPU 기기와 모바일 브라우저에서 측정한다.

Vite 등 빌드 도구 도입은 프로젝트 구조와 개발 효율을 확인한 뒤 결정한다.
도구 도입 자체를 목표로 하지 않는다.

## 3.8 저장과 멀티플레이

기존 설명상 localStorage 중심 저장과 클라이언트별 전투 계산이 한계로
제시되어 있다.

권장 진행 순서:

1.  저장 데이터 구조와 버전 관리
2.  로컬 저장 안정화 및 마이그레이션
3.  계정·인증 설계
4.  클라우드 저장
5.  플레이어 상태 동기화
6.  월드 상태 동기화
7.  몬스터 상태 동기화
8.  서버 검증 전투 및 보상
9.  재접속·복구·비정상 입력 대응

모든 연출과 계산을 서버로 옮기는 것이 아니라, 결과의 권위가 필요한
데이터(피해 판정, 보상, 인벤토리 변경 등)를 서버에서 검증하도록
설계한다.

멀티플레이 확대는 운영 비용, 보안, 동시 접속 규모를 고려해 별도
의사결정한다.

## 6.2 사용 규칙

-   라이선스와 상업적 이용 가능 여부를 개별 에셋 단위로 확인한다.

-   외부 다운로드 실패 시 존재하지 않는 파일 경로를 참조하지 않는다.
-   누락 에셋을 조용히 플레이스홀더로 대체하지 말고 개발 로그와 보고서에
    명시한다.
-   이미지 생성 결과는 콘셉트 아트일 수 있으며, 바로 사용 가능한 리깅된
    3D 모델로 간주하지 않는다.
-   실제 게임 모델은 GLB/glTF 등 프로젝트의 런타임과 호환되는 형식인지
    확인한다.

## 6.3 에셋 우선순위

1.  기존 프로젝트 에셋의 재사용 가능성 조사
2.  기존 CC0 에셋의 품질·라이선스·기술 호환성 검증
3.  게임 전체의 아트 스타일 가이드 작성
4.  플레이어와 주요 몬스터 등 화면 노출이 높은 모델부터 교체
5.  주민·NPC·환경 소품 확장
6.  애니메이션과 장비 외형 통합

# 8. Claude Code용 실행 지침

아래 프롬프트를 이 문서와 함께 Claude Code에 전달한다.

## 8.1 역할

너는 포근 마을 프로젝트의 시니어 게임 개발팀이다. 이 문서를 프로젝트의
기획·인계 기준으로 사용하되, 실제 구현 여부는 저장소를 직접 확인해
판단한다.

## 8.2 첫 작업: 분석만 수행

첫 실행에서는 소스 코드를 수정하지 않는다.

다음 작업을 수행한다.

1.  저장소의 전체 디렉터리와 파일 구조 조사
2.  실행 및 테스트 방법 확인
3.  핵심 엔트리 포인트와 Three.js 초기화 구조 확인
4.  월드 생성·청크 스트리밍 구조 확인
5.  캐릭터·몬스터·애니메이션·에셋 연결 구조 확인
6.  전투·인벤토리·장비·제작·건설 구현 확인
7.  UI·모바일 입력 구조 확인
8.  서버·WebSocket·저장 구조 확인
9.  기존 테스트 실행 및 결과 기록
10. 이 문서의 설명과 실제 구현 간 차이 기록

분석 결과를 다음 파일로 작성한다.

-   `docs/PROJECT_AUDIT.md`: 실제 코드 기반 진단
-   `docs/IMPROVEMENT_ROADMAP.md`: 우선순위 및 단계별 계획
-   `docs/ASSET_INVENTORY.md`: 에셋 목록과 라이선스 확인 현황
-   `docs/TEST_BASELINE.md`: 기존 테스트 및 실행 결과

프로젝트에 `docs/`가 이미 있다면 기존 구조를 확인하고 그 규칙을 따른다.
같은 문서가 이미 있으면 내용을 검토하고 덮어쓰기 전에 기존 정보 보존을
고려한다.

## 8.3 분석 보고서 작성 규칙

각 항목을 다음 중 하나로 표시한다.

-   확인됨: 실제 코드나 테스트에서 확인
-   일부 확인: 일부 구현은 확인했으나 완전성 미확인
-   미확인: 저장소만으로 판단 불가
-   문서와 불일치: 프로젝트 설명과 실제 구현이 다름
-   개선 제안: 아직 구현되지 않은 권고 사항

추측을 사실처럼 작성하지 않는다.

## 8.4 두 번째 작업: 계획 승인 후 구현

분석 보고서를 작성한 뒤 다음 정보를 사용자에게 요약 보고한다.

-   가장 심각한 문제 TOP 10
-   우선 작업 3개
-   예상 변경 파일
-   기존 기능에 미치는 영향
-   작업량 및 위험
-   테스트 계획

사용자의 확인을 받은 후 첫 구현 작업을 진행한다.

## 8.5 구현 규칙

-   기존 기능을 보호한다.
-   작고 검증 가능한 단위로 변경한다.
-   필요 이상으로 파일을 전면 재작성하지 않는다.
-   의존성과 버전 변경은 근거를 제시한다.
-   에셋을 추가하면 라이선스와 출처를 기록한다.
-   미구현 기능을 완료했다고 말하지 않는다.

# 9. 개발 에이전트가 지켜야 할 의사결정 원칙

1.  **기존 구현 우선 조사:** 이미 있는 기능을 중복 구현하지 않는다.
2.  **재사용 우선:** 기존 에셋과 시스템이 충분하면 재사용한다.
3.  **점진적 개선:** 대규모 전면 교체보다 검증 가능한 단위 변경을
    우선한다.
4.  **게임 재미 우선:** 기술적으로 멋진 구조보다 플레이 경험을 우선한다.
5.  **성능 예산 준수:** PC뿐 아니라 목표 모바일 기기를 고려한다.
6.  **사실 기반 보고:** 확인한 사실, 추정, 제안을 구분한다.
7.  **데이터 보호:** 저장 구조 변경 시 백업·마이그레이션·복구 방안을
    마련한다.
8.  **라이선스 준수:** 외부 에셋은 배포 및 상업적 이용 조건을 확인한다.
9.  **완료 기준 명확화:** 코드 작성만으로 기능 완료라고 판단하지 않는다.
10. **범위 통제:** 우선순위가 낮은 신규 기능은 핵심 품질 개선 후
    검토한다.

# 10. 최종 비전

포근 마을은 기능만 많은 게임이 아니라, 하나의 세계 안에서 여러 플레이
방식이 자연스럽게 이어지는 게임이어야 한다.

플레이어가 경험해야 할 핵심은 다음과 같다.

-   아름다운 마을에서 여유로운 생활을 한다.
-   새로운 지역을 탐험하며 발견의 즐거움을 느낀다.
-   강력한 몬스터와 긴장감 있는 전투를 한다.
-   희귀 장비와 재료를 얻고 캐릭터를 성장시킨다.
-   나만의 집과 거점을 만든다.
-   동물과 공룡을 길들이고 함께 모험한다.
-   주민들과 관계를 쌓고 마을을 발전시킨다.
-   장기간 플레이해도 새로운 목표와 보상을 발견한다.

그래픽, 게임성, 기술적 안정성은 서로 분리된 목표가 아니다. 모두 하나의
일관된 플레이 경험을 만들기 위해 발전시킨다.

**첫 번째 실행 목표는 신규 기능 개발이 아니라 실제 저장소의 정확한
진단이다.**

분석 → 우선순위 합의 → 작은 단위 구현 → 테스트 → 결과 보고의 순환을
유지한다.

# 11. 최초 실행용 짧은 지시문

아래 내용을 Claude Code의 첫 메시지로 사용한다.

> 현재 저장소의 포근 마을 프로젝트를 `docs/PROJECT_HANDOFF.md`의
> 기준으로 분석해 줘.
>
> 지금은 어떤 소스 코드도 수정하지 마.
>
> 실제 파일과 코드를 조사해서 문서에 적힌 기능이 구현되어 있는지
> 확인하고, 문서와 실제 구현이 다른 부분도 찾아줘.
>
> 실행 가능한 기존 테스트를 먼저 실행하고 결과를 기록해 줘. 테스트를
> 실행할 수 없는 경우 그 이유를 명시해 줘.
>
> 분석 결과를 바탕으로 심각도와 기대 효과를 고려한 개선 우선순위 TOP 10
> 및 단계별 로드맵을 작성해 줘.
>
> 특히 캐릭터·몬스터 그래픽, 전투·파밍, 오픈월드 콘텐츠 밀도, 모바일
> 성능, 저장 구조를 중점적으로 검토해 줘.
>
> 확인된 사실과 추정, 개선 제안을 구분하고, 첫 분석이 끝나면 수정 파일
> 없이 보고해 줘. 이후 구현 순서는 별도로 결정하자.

## 문서 사용 방법

1.  이 파일을 프로젝트 루트에 `docs/PROJECT_HANDOFF.md`로 저장한다.
2.  기존 `PROJECT_PROMPT.md`는 원본 기획 자료로 보존한다.
3.  Claude Code에서 프로젝트 루트를 연다.

    검토한다.

기준이다. 실제 저장소, GitHub, 실행 환경을 조사한 결과가 아니므로 구현
현황이나 테스트 통과를 보증하지 않는다.
