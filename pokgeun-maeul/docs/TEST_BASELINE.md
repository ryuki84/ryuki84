# 테스트 기준선 (TEST_BASELINE)

- 실행일: 2026-11-27
- 대상 커밋: `15f0526` (브랜치 `ccr-a192749b-nh5md0`, 소스 미수정)
- 실행 환경: 클라우드 리눅스 컨테이너. Chromium(Playwright)에 **소프트웨어 WebGL(SwiftShader, GPU 없음)**. 화면 크기는 기본 960×640, 모바일 시나리오는 iPhone 13 에뮬레이션.
- 실행 방식: three.js r187을 CDN 대신 로컬 npm 패키지로 공급했어요. Google Fonts 요청은 차단했어요. 대부분 시나리오는 빠른 실행을 위해 `?style=toon`(툰 렌더링)으로 돌렸어요.
- ⚠️ 테스트 스크립트는 **저장소가 아니라 작업 환경의 임시 폴더**에 있어요. 다른 환경에서 재현하려면 먼저 저장소로 옮겨야 해요(로드맵 작업 A).
- ⚠️ 소프트웨어 렌더링 결과라서 **실제 기기의 성능이나 그래픽 품질을 보장하지 않아요.** 측정 중 프레임은 약 2~7fps였어요.

## 실패 분석 (추가 확인)

- **서버 테스트(mp, m4)**
  - 페이지 하나만 서버로 열면 3.4초 만에 준비돼요.
  - 첫 번째 클라이언트가 마을·월드를 소프트웨어로 렌더링하는 동안 두 번째 탭이 30초 넘게 기다려요.
  - 구역 생성 시간은 처음 22ms, 이후 약 5ms였어요. 생성 자체보다는 **소프트웨어 렌더링의 CPU 점유** 때문일 가능성이 높아요.
  - 다만 한 맵 통합 이후 마을에서도 월드 청크를 함께 그리게 되면서 렌더링 부하가 커진 영향일 수 있어요. 실제 기기에서 프레임을 재야 확정할 수 있어요(미확인).
- **k4, tp**: fps 2 수준에서 시간 기반 대기가 부족한 테스트 설계 문제로 보여요. 다만 실제 버그일 가능성도 배제하지 못했어요. 작업 A에서 "시간 대기" 대신 "상태 조건 대기"로 바꾼 뒤 다시 판정할게요.
- **seam (실사)**: 테스트의 스크린샷 시간 제한 문제예요. 기능 실패는 아니에요.

## 이번 기준선에 포함하지 않은 것

- 실제 GPU 기기·모바일 브라우저 실행과 fps 측정: 이 환경에서는 불가능해요.
- 장시간 실행 메모리 증가: 측정 도구가 없어 미실시예요.
- 오디오 출력: 소리를 들을 수 없어 미확인이에요.
